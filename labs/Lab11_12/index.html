Lab 11/12 — Three Formats, One Model

Lab thesis: a model file is a live in-memory object flattened onto disk. This lab makes you measure what that flattening costs and what it throws away — by saving one model three ways and watching the numbers that only differ because the formats differ.

This is the experimental half of Lecture 11/12 — Model artifacts. The lecture argued that each format keeps a different amount of the live object, and pays for it differently. Here you produce those differences as measurements on a machine you control.

Runs on Google Colab (free) or your own machine — no GPU required. This lab is CPU-only; the disk, the page cache and the allocator are what you are measuring.

Open the notebook in Colab · read it on this site · download from GitHub

What this is not

It is not the lecture's demo notebook re-run. The demos showed you a transpose costs nothing and a mmap load costs almost no memory. Here you predict every number before you look, then explain the gaps:

The lecture showed This lab makes you produce
a .pt is a zip holding a pickle + storages the same model as .pt, .safetensors, .gguf, sized and timed by you
mmap loads without copying the RSS and rchar gap between a read() and a mmap, on your machine
.contiguous() is a real copy the cost curve of that copy against tensor size — predicted first
pickle executes on load the payload firing, then blocked — and one paragraph on what safetensors did not fix

What you need

  • Python 3.10+, torch, safetensors. A .gguf of any small model (an Ollama blob works — see Part 4).
  • Linux or macOS for the /proc and RSS readings in Part 1; on Windows, run Part 1 on Colab.
  • No GPU. No lab hardware.

What you do

Part 1 — The load path (40 marks)

Materialize one model (your choice, ≥ 100 MB of weights) three ways: .pt, .safetensors, and — via a conversion tool or a download — .gguf.

For each, predict then measure: file size · cold-cache load time · warm-cache load time · resident-memory delta · bytes read via /proc/self/io rchar.

You are marked on establishing these relationships between your own numbers, not their magnitudes:

Relationship Why it holds on any machine
warm load ≪ cold load the page cache is doing the second read
safetensors RSS delta ≪ file size mmap maps; it does not copy
rchar ≈ 0 for a mmap load, ≈ file size for an explicit read() mmap issues no read syscall
.pt RSS delta ≈ file size pickle materialises the object graph

Part 2 — The stride tax (25 marks)

Build a large non-contiguous tensor (a transpose, or a slice with a gap). Predict the cost of saving it before you measure it.

Show that:

  • the transpose itself moves zero bytes (data_ptr unchanged),
  • .contiguous() cost scales with the bytes moved, and
  • safetensors refuses the view and accepts the packed copy.

One paragraph: who the format made pay for contiguity, and why that is the right place to put the cost.

Part 3 — The trust boundary (20 marks)

Ship a .pt carrying a benign __reduce__ payload that writes a file in the lab's own working directory. Demonstrate it firing on load. Show torch.load(weights_only=True) blocking it. Convert the same weights to safetensors.

One paragraph, and it is the point of the part: what safetensors removed, and what it did not — name at least two things a safetensors file still cannot protect you from.

Keep every payload confined to writing inside the lab directory. A payload that touches anything outside it fails the part.

Part 4 — Read a real file (15 marks)

Point a GGUF parser (the lecture notebook's, or your own) at an actual .gguf — an Ollama blob under ~/.ollama/models/blobs/, or any download.

Report: the architecture hyperparameters and the tokenizer vocabulary size you read out of it, and which metadata value types your parser cannot handle and what they are for.

What you submit

Two files. The JSON carries your measurements; the notebook carries your reasoning.

  1. submission_lab11_12_<roll>.json — written by the notebook's final cell. Set ROLL_NUMBER and NAME first.
  2. The executed notebook — outputs intact, every 📝 prediction and explanation cell filled in.

Run every cell top to bottom before exporting.

How it is marked

Automatic (from your JSON) — each check tests a relationship between your own numbers, because your disk, RAM and allocator are yours:

  • warm load < cold load
  • safetensors RSS delta < ¼ × file size
  • read() rchar ≈ file size; mmap rchar ≈ 0
  • .contiguous() time rises with tensor size
  • the payload is blocked by default and fires only under weights_only=False

Rubric (from your written cells) — predictions marked for being made, explanations for naming the mechanism: page cache, mmap, allocator copy, name resolution, allow-list. The heaviest single item is Part 3's paragraph on what safetensors does not fix — a format claim with no threat model behind it scores about half.

40 automatic + 60 rubric, out of 100. The automatic half is marked by code/artifacts/grade_lab11_12.py from the JSON your notebook's export cell writes.

An honest surprising measurement, correctly explained, scores higher than a tidy expected one. If your machine's page cache was already warm and cold ≈ warm, say so and explain it.

Academic integrity

The measurement vector (sizes, timings, RSS, rchar) is machine- and run-specific; two independent runs never match. Submissions sharing a measurement vector are treated as copied. Discussing mechanisms is encouraged; sharing measurement files is not.
