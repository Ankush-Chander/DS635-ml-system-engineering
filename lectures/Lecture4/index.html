Tensor Cores, Precision, and the Execution Model

Module thesis: modern ML performance is a bandwidth problem wearing a compute problem's clothes.

The machine the ladder was imitating

Two lectures ago you designed this machine from the workload; last lecture you built its tricks by hand on a CPU. Now meet it.

Read the figure left to right:

  • CPU side: 4 cores, and in each one the Control block is as big as the ALU, plus a private L1 and a large shared L2/L3 — one full set of control machinery per arithmetic unit
  • GPU side: each row is one repeating building block — a tiny Ctl + L1 slice driving a whole row of ALUs. Control cost amortized across dozens of units; the chip is this row stamped out ~100 times
  • Cache demoted: the GPU's L2 is a thin strip, not the dominant area — caches are not its answer to the memory wall
  • Two memories, one narrow bridge: each side has its own DRAM, joined only by PCI-Express — far slower than either memory. That's the transfer tax the ladder's --time-transfer trap measured

The trade, in numbers — throughput = units × ops/unit/cycle × clock:

  • CPU: ~32 cores × ~16 ops/cycle each × 5 GHz ≈ a few TFLOPS peak
  • GPU (H100): ~16,000 FP32 units × 2 (FMA) × 1.8 GHz ≈ ~60 TFLOPS — same transistor technology, opposite bet

Each GPU thread is much slower than a CPU thread. The CPU minimizes time to finish one thing; the GPU maximizes things finished per second.

And its answer to the memory wall — the caches are gone, yet DRAM still takes ~300 cycles. The GPU's move: keep far more groups of work resident than can execute, each with registers parked on-chip; when one group stalls on a load, switch to another next cycle, for free. The CPU hides latency (caches + prediction make the wait short); the GPU tolerates it (someone else is always ready to run). It can afford this only because the workload has millions of independent items — property 1 from the derivation, cashing its check.

CPU GPU
Optimized for latency of one stream throughput of millions of items
Cores ~dozens, fast, clever ~thousands, slow, dumb
Control predict, reorder, speculate one decoder drives a lockstep group
Answer to memory wall caches + prediction don't wait — switch to other work
Analogy a few professors thousands of school kids doing arithmetic

Three unsolved mysteries from the matmul ladder

  1. The TF32 flag did nothing on the RX 6700M (8,677 ≈ 9,022 GFLOP/s — within noise)
  2. FP16 halved the bytes but delivered only 1.7×, not 2×
  3. Without synchronize(), we "measured" 314 µs for work that took 1.9 ms — an implied 55 TFLOP/s on a 10.6 TFLOP/s GPU

This lecture resolves all three.

Tensor cores — the ladder's missing rung

  • The progression we already climbed: scalar FMA (1 value/instruction) → SIMD (8 values/instruction) → tensor core: an entire matrix block per instruction
    • One MMA instruction: D = A×B + C on a small tile (e.g. 16×16), systolic-style
  • Why it wins: the SIMD amortization argument taken to its extreme — one fetch/decode for a whole tile of FMAs, plus operand reuse inside the unit
  • The numbers: H100 ≈ 67 TFLOP/s (FP32 vector pipes) vs ≈ 990 TFLOP/s (FP16 tensor cores) — ~15×
  • The whole chip really is built around matmul

💬 Mystery 1: why did allow_tf32 = True do nothing on our laptop?

Answer
  • RDNA2 has no tensor cores — the flag toggled hardware that isn't there.
  • Dedicated matrix units: NVIDIA (Volta+), AMD CDNA / RDNA3+ (WMMA), Google TPUs. On everything else, TF32 silently falls back to the FP32 pipes.

The precision ladder

  • Bit layouts (sign + exponent + mantissa):
    • FP32: 1 + 8 + 23
    • TF32: 1 + 8 + 10 — FP32 range, FP16 precision, tensor-core speed
    • FP16: 1 + 5 + 10
    • BF16: 1 + 8 + 7
    • FP8: E4M3 / E5M2 (training frontier)
  • What halving the bits buys — twice:
    • Half the memory footprint and half the bandwidth demand (directly relieves the memory wall)
    • Roughly double the tensor-core throughput
  • Exponent bits = range; mantissa bits = precision

💬 Mystery 2: FP16 halves every byte moved. Why only 1.7× and not 2×?

Answer
  • The multiply isn't everything: kernel launch, index arithmetic, cache effects, and accumulation (often still FP32) don't halve.
  • Rule of thumb all term: speedup from an optimization is capped by the fraction of time spent on the thing optimized (Amdahl, in bandwidth clothes).

Why BF16 won

  • FP16's failure mode: 5 exponent bits → max value 65,504
    • Demo, one line: np.float16(70000) → inf
    • Gradients overflow → loss scaling workaround (multiply loss up, gradients down)
  • BF16's bet: keep FP32's 8-bit exponent (same range, drop-in), sacrifice mantissa
    • SGD is noisy anyway — training tolerates the lost precision
  • Mixed precision — the industry default recipe:
    • Compute in BF16/FP16 · keep FP32 master weights · accumulate in FP32
  • Where lower precision is not free: outlier activations, small models (production quantization: Module 4)

Shape and alignment constraints

  • Tensor cores consume fixed tile shapes — odd or misaligned dimensions fall off the fast path
  • This is why hidden dimensions are multiples of 64/128 (GPT-3's vocab: padded to a multiple of 128)

💬 Your model's hidden dim is 4097 instead of 4096. What happens to throughput?

Answer
  • The matmul no longer maps cleanly onto tensor-core tiles — the library pads or falls back to slower kernels; throughput can drop by an integer factor.
  • One dimension, one unit off. Check your shapes.

Kernel launch is an asynchronous enqueue

  • C = A_g @ B_g enqueues work on a stream and returns immediately — the GPU executes later
  • torch.cuda.synchronize() = wait for the queue to drain
  • Mystery 3 resolved: the 314 µs was the enqueue, never the compute — a GPU "beating" its own peak is the tell
  • Launch overhead is ~5–10 µs per kernel → a model issuing thousands of tiny kernels drowns in launches
    • This is why operator fusion exists — next lecture

Recap

  • Tensor cores: matmul as a single instruction — the ladder's endpoint
  • Precision: fewer bits = less bandwidth = more speed; exponent = range, mantissa = precision; BF16 = range over precision
  • Execution: launches are async enqueues; always synchronize before timing
  • Next: the software stack — compilers, fusion, and kernels
